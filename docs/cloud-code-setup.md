# Cloud Code — trophy attestation

The trophy submission in `LeaderboardManager` used to be one-sided: whichever client claimed
it won wrote the score itself, so a modified client could set any number it liked. The host
being the authority does not help here — a cheating host *is* the authority.

`CloudCode/submit-match-result.js` closes that. Both players report their **own** result for
the same match; trophies move only when the two reports agree that one beat the other. A
single lying client is no longer enough — it would have to collude with the opponent it just
beat or lost to.

Until the module is deployed the client falls back to the old direct submission, so nothing
is broken by shipping this before the deploy.

## What is already in the client

| Piece | Where |
|---|---|
| Unique match id, generated by the host | `TurnManager.Attestation.cs` → `netMatchId` |
| Both players' real UGS PlayerIds, broadcast to both machines | `TurnManager.BroadcastRoster` → `SyncMatchRosterClientRpc` |
| The Cloud Code call, with fallback | `Assets/Scripts/Cloud/MatchAttestation.cs` |
| The call site | `LeaderboardManager.ReportOnlineMatchResult(won, matchId, opponentId)` |
| Package | `com.unity.services.cloudcode` 2.10.4 (`Packages/manifest.json`) |

The host also registers its **own** PlayerId now: `NetworkIdentityRegistry` only ever
received identities from remote clients, so before this the roster had a hole where the host
should have been.

## Deploying the module (needs the account owner)

This cannot be done from a headless session — every step below needs an interactive Unity
login. Expected account: `yilkgamesstudio@gmail.com` (see `C:\Projects\pictures\STUDIO.md`;
check which Google account the browser is in **before** starting).

1. Install the CLI: `npm install -g ugs` (or download the `ugs` binary from Unity).
2. `ugs login` — sign in with the studio Unity account.
3. From the project root:
   ```
   ugs deploy CloudCode/submit-match-result.js --project-id <PROJECT_ID> --environment production
   ```
   The project id is the one in `ProjectSettings/ProjectSettings.asset` → `cloudProjectId`.
4. In the Unity Dashboard, confirm the script appears under **Cloud Code → Scripts** with the
   name `submit-match-result` — `MatchAttestation.ModuleName` must match it exactly.
5. The module writes to Cloud Save **custom** data under `matches/match_<matchId>`. Custom
   data has to be enabled for the project (Dashboard → Cloud Save → Custom Data).
6. The leaderboard id it writes is `cosmic_trophies`, the same constant the client uses
   (`LeaderboardManager.LeaderboardId`).

## Verifying it (the part that still has to be done live)

The module can only be verified with two real processes, which is also how every other
multiplayer milestone in this project was signed off:

1. Open the Unity Editor, build a second player (or use Multiplayer Play Mode).
2. Play a **ranked** quick match to a real finish.
3. Expect: the loser's client reports first or second, and the record under
   `matches/match_<id>` ends with `applied: true`; both players' `cosmic_trophies` entries
   moved by +30 / −20.
4. Then the cheat case: run one side with a modified result and confirm the record comes back
   `rejected` and **no** trophies moved.

Until step 4 has actually been run, treat the protection as written-but-unverified.

## Still one-sided: the economy

The same exposure remains for gold/gems/XP: `CloudSaveManager.PushAsync` writes whatever the
client holds in memory, and the local HMAC only protects the file at rest. The fix has the
same shape — move `CurrencyManager.Add`/`Spend` behind a Cloud Code module so the client asks
for a reward instead of announcing a balance — but it touches every economy call site, so it
is deliberately not started here. See `TODO.md` item 22 / audit item 6.
